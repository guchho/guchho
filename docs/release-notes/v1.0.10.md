# Guchho 1.0.10

**Released 2026-11-15.**

## Added

### `guchho test`

`guchho test` runs tests through the optional
[`@guchho/test`](https://github.com/guchho/test) runner. It is handled by the
npm entry point before guchho loads a build engine, and every argument after
`test` is passed through unchanged:

```bash
guchho test
guchho test watch
guchho test src/math.test.ts
guchho test run --filter math --reporter=verbose
```

`@guchho/test` is an optional peer dependency, not part of a normal guchho
install. When it is missing the command prints how to add it:

```bash
npm install --save-dev @guchho/test
```

The runner requires Node.js 20.19 or newer. Guchho itself continues to support
Node.js 18; only the `test` command needs the newer runtime. Node resolves the
runner from the project or from the guchho installation, so the command is for
npm-managed projects. Binary-only distributions such as zip, Chocolatey,
Homebrew and WinGet do not go through the npm entry point and do not provide
`guchho test`.

| Exit code | Meaning |
| --- | --- |
| `0` | All selected tests passed. |
| `1` | A test failed, a coverage threshold was not met, or `@guchho/test` is not installed. |
| `2` | The runner rejected the command line or could not discover or execute tests. |

See [`guchho test`](../reference/cli/test.md) for the full command reference.

### Archives in `@guchho/wasm`

The WebAssembly package now exposes the archive operations the native package
already had. `pack()` and `unpack()` take the same options as their native
counterparts, but every path is a path inside the engine's filesystem: the host
tree under `/host` on Node, and `/` with a `files` map in the browser.

```js
import { pack, unpack, packBytes, unpackBytes } from "@guchho/wasm";

await pack({ inputs: ["dist"], outFile: "release.zip", level: 9 });
await unpack({ archive: "release.zip", outDir: "check" });

const { bytes } = await packBytes({ inputs: ["dist"], format: "tar.gz" });
const { files } = await unpackBytes(bytes, { format: "tar.gz" });
// files is { "dist/index.html": Uint8Array, ... }
```

- **`pack(options)`** - `inputs` and `outFile` are required. `format` (`zip`,
  `tar`, `tar.gz`), `level`, `overwrite`, `date` and `mode` match the native
  `pack()`.
- **`unpack(options)`** - `archive` is required. `outDir`, `format`,
  `overwrite`, `stripComponents`, `preservePermissions` and
  `preserveTimestamps` match the native `unpack()`.
- **`packBytes(options)`** - the same options without `outFile`; resolves with
  the archive as a `Uint8Array` and any warnings.
- **`unpackBytes(bytes, options?)`** - the same options without `archive` or
  `outDir`; resolves with the extracted files as `{ path: Uint8Array }` and any
  warnings.

`packBytes()` and `unpackBytes()` keep the archive and the extracted files in
memory, so both directions work in a browser, where there is no host disk to
name. The `guchho` package's browser entry now supports `pack()`; its
`unpack()` still throws because it writes to a host filesystem. Use
`unpackBytes()` from `@guchho/wasm` when extracting in the browser.

### Plugins can shape the build from `buildStart`

A `buildStart` hook runs before any file is read, which makes it the one place a
plugin can hand the build something that does not exist on disk. It may now
return entry points and extra watch paths:

```js
export default {
  name: "virtual",
  buildStart() {
    return {
      entries: ["virtual:entry"],
      watchFiles: ["src/template.html"],
      watchDirs: ["src/partials"],
    }
  },
  resolveId(id) {
    if (id === "virtual:entry") return id
  },
  load(id) {
    if (id === "virtual:entry") return "export default 1"
  },
}
```

- **`entries`** accepts the same spellings as the `entrypoints` option: a path,
  an `{ in, out }` record, or `[out, in]`. Contributed entries are merged with
  the configured ones rather than replacing them, and are resolved by the same
  rules, so a plugin can supply a virtual module as an entry.
- **`watchFiles`** and **`watchDirs`** are merged into the same dependency set
  the resolver and loader already feed, so a change to either triggers a
  rebuild.
- **`this.addWatchFile()`** now does the same for a single file. It previously
  recorded the intent without passing it back to the engine.
- **`this.meta.watchMode`** now reports whether the current pass is a watch
  rebuild, instead of always being `false`.
- **Emitted assets** with a relative name are written under the output
  directory, the way Rollup treats them, and `generateBundle` and `writeBundle`
  receive `{ dir }` as their output options.

From C++, `api::OnStartResult` gains `entries`, `watch_files` and `watch_dirs`,
with the matching fields on `config::OnStartResult`.

### Plugins can transform modules

A `transform(code, id, info)` hook runs after a module's source has been loaded
and before the parser sees it. Every matching transform runs in plugin order and
receives the text the previous one produced, so a chain of small rewrites stays
predictable. Return a replacement string or `SourceDescription` to change the
source, or `null` to decline.

```js
export default {
  name: 'stamp',
  transform(code, id, info) {
    if (info.loader !== 'js') return null
    return { code: code.replace('__BUILD__', '"1.0.10"') }
  },
}
```

`info` carries the module's `namespace`, `suffix`, `loader`, import `with` values
and the `meta` value left by `resolveId` or an earlier transform. A returned
`SourceDescription` may also carry a JSON `map`, `meta` for later hooks, and
`watchFiles`/`watchDirs`. When source maps are enabled, a map becomes the
module's input source map and is used in preference to a `sourceMappingURL`
comment. `copy` and `binary` modules are not transformed, and a hook that throws
fails the build with its own message.

From C++, register the same hook with `PluginBuild::on_transform`, using
`OnTransformOptions`, `OnTransformArgs` and `OnTransformResult`.

### Virtual modules in one step

`resolveId` plus `load` remains the general way to supply a module in memory.
`buildStart` can now register one directly, either through
`this.addVirtualModule()` or in a `virtualModules` array in its result:

```js
export default {
  name: 'generated-config',
  buildStart() {
    this.addVirtualModule({
      id: 'virtual:config',
      namespace: 'virtual',
      suffix: '?raw',
      loader: 'js',
      resolveDir: 'src',
      code: 'export const value = 1',
      watchFiles: ['config.json'],
    })
  },
}
```

`id` and `code` are required; `code` may be a string or `Uint8Array`.
`namespace` defaults to `"virtual"`, `loader` defaults to `"js"`, and
`resolveDir` is the base for the module's own relative imports. `suffix` must
start with `?` or `#` and is part of the module's identity without being part of
its name. `meta` is carried to the module's hooks, and `watchFiles`/`watchDirs`
add dependencies.

A registered module answers an import whose specifier is its `id` or
`id + suffix`, and its contents come from the registration instead of a file.
An empty id, a malformed suffix, or two modules with the same namespace, id and
suffix fail the build with the plugin names in the message. From C++, add
`api::VirtualModule` values to `api::OnStartResult::virtual_modules`.

### Plugins can ask the build to resolve

`this.resolve(source, importer, options)` now answers with the same resolver and
plugin chain the build uses, instead of rejecting with a sentence naming the
limitation:

```js
export default {
  name: 'asker',
  async transform(code, id) {
    const found = await this.resolve('./helper.js', id)
    return found === null ? code : code.replace('HELPER', found.id)
  },
}
```

The question is a nested request on the same service connection, so it stays
with the right build even when a watch session has several rebuilds in flight.
By default `custom: true` is sent and the calling plugin is skipped, so a plugin
that rewrites imports cannot answer its own question and loop forever. Pass
`custom: false` when that is what is wanted. `options` may also name a
`namespace`, `resolveDir`, `kind` and import `with` values. `load` and
`transform` hooks receive those `with` values through `info.with`.

## Fixed

### Source-map generation no longer crashes

Building with source maps could read out of bounds when a file had no line
offset entries, or when a location preceded the first line. Both cases left the
line index negative, which the chunk builder then used to index the line table.
Those mappings are now skipped: a location the inputs cannot map produces no
mapping instead of crashing the build.

### Lowered logical assignments keep their declaration

Lowering `||=`, `&&=` and `??=` for an older target duplicates the left-hand
side. When the left-hand side was a local variable, the syntax minifier did not
see the duplicate use, so it could inline an uninitialized `let` as `void 0`
and then remove the declaration:

```js
// Original
function foo() {
  let x
  bar(x ||= {})
}

// Before: "x" is assigned but never declared
function foo() {
  bar(void 0 || (x = {}));
}

// After
function foo() {
  let x;
  bar(x || (x = {}));
}
```

The lowering now counts the duplicate reference, so the declaration survives.

### Template literals lex again

The `lex-js` compiler command now handles interpolated template literals. The
lexer emits a close brace for the end of each `${...}` substitution and needs
that brace rescanned before it can read the following template text. The
service did not ask for the rescan, so the text after the brace looked like an
unterminated string:

```js
const greeting = `Clicked ${count} times`
```

That failure surfaced in the playground as `Lex failed: [object Object]`,
because a lexer panic is not a `std::exception` and the WebAssembly boundary
turned it into an object with no message. The service now tracks nested
substitutions and brace depth, returns the lexer's own diagnostic along with
the tokens found before the failure, and converts any remaining engine
exception into a normal error response.

### TypeScript parses in the playground

The playground sends TypeScript, JSX and TSX source through `parse-js` because
all four are JavaScript-family languages. The handler parsed every request as
plain JavaScript, so the default TypeScript sample reached the parser with
`interface`, type annotations and typed parameters and failed with:

```text
0 part(s) · parse failed · 1 ms
```

`parse-js` now retries with the TypeScript, JSX and TSX parser modes when the
plain JavaScript parse fails, and keeps the original JavaScript diagnostics
when none of them accepts the source. A request can also set `typescript` or
`jsx` directly, or name a `sourcefile` whose extension selects the dialect.

### Watch mode begins with a build

`guchho watch`, `guchho build --watch` and `guchho serve` now run an opening
build as soon as they enable watch mode. Watch mode records paths only on
passes that run after it is enabled, so without that pass the watcher started
with an empty set. In practice `guchho serve` did not notice a change until a
browser had requested a page, and the other commands waited for a rebuild
before they were watching anything. The opening build gives the watcher its
initial paths directly.

### Plugin hooks keep their options alive

A context passed plugin setup a pointer to its initial `BuildOptions` that lived
only until `Context()` returned. A hook reading `initial_options` afterwards —
including the `WatchMode` flag — was reading freed memory. The context now owns
the options for the life of the session, so hooks see the real values and
`WatchMode` reaches them on watch builds and rebuilds.

## Distribution

- AIX PPC64 is now a build and publish target. AIX has no hosted GitHub runner
  and no public Linux cross toolchain, so it builds on a self-hosted runner
  labelled `self-hosted`, `aix` and `ppc64`.
- Homebrew packaging scripts generate, validate and publish a source-build
  formula.
- WinGet manifest tooling generates the installer manifests for submission to
  `microsoft/winget-pkgs`.

## Upgrading

Nothing here is breaking for users of 1.0.9. Upgrade to pick up `guchho test`,
the archive API in `@guchho/wasm`, and the new plugin hooks for transforms,
virtual modules and resolution:

```bash
npm install -g guchho@1.0.10
npm install -D @guchho/wasm@1.0.10
npm install -D @guchho/test
```

The last line is only needed if you want to use `guchho test`.
